# 产品路线与技术方案架构复核

> 日期：2026-10-17。对象：[产品路线图](./product-roadmap.md)、[技术方案](./technical-roadmap.md)及 [VCPChat 评估](./vcpchat-reference-assessment.md)。代码核对基于 Hertz 提交 `79b15d48c2e072342e7efac3c5b723e62623de9f`。
>
> 本次是源码与设计的静态复核，没有实现 AI/MCP、安装 SDK、执行产品测试或进行声卡/模型测量。下文“已修订”表示方案已改，不表示代码问题已经修复。涉及未来任务系统的风险属于设计缺口，不是当前播放器已发生的故障。

## 1. 结论与修订范围

Rust 服务、现有浏览器前端、SQLite、本地优先和原音频 actor 的总体方向适合本项目。移除 Node 后，原方案仍有若干实质缺口，主要集中在状态归属、异步副作用、预算恢复及现有代码事实。没有必要因此更换技术栈或增加新的编排框架。

| 编号 | 问题 | 优先级 | 本次处理 |
| --- | --- | --- | --- |
| AR1 | 现有 HTTP/RPC 播控重复，Ok 不一定代表本次动作已提交 | P1，开放播控前 | 收敛共享入口，补精确结果和服务端执行生命周期 |
| AR2 | intent 隐式依赖当前预置，预览可能触发自动保存 | P1，开放草稿前 | 明确 create 基线，抽出纯物化，增加不落盘的临时层 |
| AR3 | 收费请求崩溃窗口缺乏持久派发事实 | P1，真实模型前 | 派发前记账标记，恢复时保守结算且不重发 |
| AR4 | 任务取消终态被误当作连接/执行资源已经释放 | P1，任务底座 | 槽位覆盖本地清理，任务状态与资源状态分开 |
| AR5 | 每主体月预算可能被多个 grant 和官方入口叠加 | P1，真实模型前 | DataDir 总预算与总熔断，主体只做权限和归因 |
| AR6 | 应用内 AI 和草稿被不必要地绑定到 MCP 阶段 | P2，任务拆分时 | 服务直接装配，公共模块独立，移除硬依赖 |
| AR7 | 专用授权路由、监听范围与付费 HTTP 客户端边界未落清 | P1，外部/云开放前 | 独立路由认证、限制首发绑定、专用模型客户端 |
| AR8 | 改用单源搜索会绕开旧聚合的 6 秒期限 | P1，R1 发布前 | 共享入场与总期限下沉到实际单源搜索路径 |
| AR9 | 音频专项过早定义全链重排，与当前 DSP 所在域不符 | P2，S1 启动前 | S1 只换解码侧重采样，保留现有设备域处理 |

以上修订已直接写回产品和技术文档。开发阶段仍需用相应反例证明实现满足这些约束。

## 2. AR1：先共享播控业务，再增加第三种入口

**源码事实：** [HTTP 播控](../crates/hertz-studio/src/routes.rs)、[RPC 播控](../crates/hertz-studio/src/rpc/playback.rs)中的 play/pause/seek 仍分别操作 play_commit、代际、audio 和 transport_committed。`state.rs::step` 将 play_index_for 的 PlayOutcome 映射成 `()`，队列为空等分支也可返回 Ok；旧 play 在没有已装载曲目时还会恢复队列并加载。

**原方案风险：** 再写 MCP 版控制逻辑，会出现三份锁和播放代际规则。直接将 RPC 的 Ok/200 映射为 applied，会把无操作或被其它意图取代当成成功；复用旧 play 作为严格 resume 还会意外发起加载。8 秒工具等待和更长的在线准备流程也不能共用一个取消生命周期。

**已修订：** 只将本轮六种动作下沉为小型共享应用函数，返回已提交、无操作、被取代或失败；保留旧 API 的兼容响应。严格 resume 仅作用于已装载曲目。MCP 消费因果结果和经授权投影的快照，不从快照猜测本次动作的完成。变更由服务端有界 owner 持有去重记录、许可和清理责任，调用者断开只结束等待。

**实施验证：** 空队列 next、未装载 resume、单曲循环、新播放意图取代旧准备、调用者超时、重复 clientOperationId、准备取消后 cursor/buffering/缓存回收。

## 3. AR2：补丁语义和草稿语义必须分开

**源码事实：** [creative-stage.js](../plugin/ui/creative-stage.js)的 applyIntent 从 `deep(preset)` 起步；只有切换到不同场景时才重置部分参数。applyIntent 和 setPreset 都调用 saveLocalSoon，后者约 400ms 后将当时 preset 写入 localStorage。

**原方案风险：** 同一 intent 在不同当前 preset 上产生不同结果；仅携带 basePresetHash 并不会自动选择对应基线。若用 setPreset 暂时展示候选，等待确认期间就可能保存候选，刷新后变成“尚未确认却已应用”。

**已修订：** 新 AI/导入首期只做 create：目标 scene、可信默认基线、版本与 hash 均明确。原前端内抽出 `materializeIntent(basePreset, intent)`，只产出候选和诊断；旧规则入口保留对当前舞台编辑的语义。原 owner 管理临时呈现层，持久化始终读取 committed preset，确认应用后才提交。首期不在预览面板并发调参，其它编辑先使预览失效。

这仍然是一份前端物化实现，不是在 Rust 重写舞台逻辑，也不需要浏览器外 JS 引擎。

**实施验证：** 不同当前 preset 下 create 结果一致；超过保存延迟、切页、刷新、退出、旧保存 timer 在途和取消时，未确认候选都不能落盘；旧分享与原规则入口不回归。

## 4. AR3：本地事务不能证明远端尚未扣费

**设计事实：** 任务持久化、原始描述仅在内存、重启改为 interrupted 都合理，但它们没有说明崩溃发生时网络是否可能已发出。SQLite commit 与远端模型请求之间没有共同事务。

**原方案风险：** 恢复时把 interrupted 一律视为未调用，释放预留并允许继续消费，会低估真实费用；若自动重发，又可能重复扣费。仅增加 running 状态不足以关闭这个窗口。

**已修订：** 网络调用之前持久化 `dispatchState=may_have_been_sent`、attemptId 和费用快照；一个 job 最多一次派发。未派发任务可释放预留，可能已派发且 usage 不明时按预留保守入账。即便标记后、实际发出前崩溃也可能留下估算费用，应明确显示，不能编造精确结算。

另将 DB commit 与内存输入交接纳入服务端受理 owner：先拿有界容量，commit 后不随 HTTP waiter 一起丢弃输入；进程内交接/worker 故障也必须收敛，不能留下永久 accepted。

**实施验证：** 容量预留、DB commit、内存交接、派发标记、网络调用和终态落库前后分别注入故障；无重复 POST、无预留双计/误释放、无无法收敛的 accepted。

## 5. AR4：取消任务不代表资源已经结束

**设计事实：** 用户取消、请求超时、关闭流和远端停止推理是不同事实。即使本地终态已写入，连接或 worker 仍可能等待清理；远端甚至可能继续运行。

**原方案风险：** 用“任务非 running”作为释放单并发槽的条件，连续取消可以产生多个仍在运行的请求；旧 worker 迟到结果也可能与新任务争抢资源。反过来，无期限等待“远端确认停止”会把队列永久卡住。

**已修订：** 本地执行许可覆盖调用和回收，由执行 owner 管理，UI 终态不直接释放许可。清理有界，无法收口时暂停新生成并显示诊断。单并发仅保证本地受管请求数，不能宣传为远端推理全局单并发。费用按派发事实独立处理。

迟到 usage 只能来自已有受管响应，或指定 provider 确实支持的按请求身份查询；没有接口时保留估算，不建设假的通用自动对账。

**实施验证：** cancelled/expired 已落库而 future 未退出、慢清理、连续取消、迟到响应、无 usage 查询接口及断网恢复。

## 6. AR5：5 美元必须是 DataDir 总上限

**原方案风险：** `owner/principal/month` 若各有 5 美元，会让两个 grant 加官方 UI 得到多份预算；轮换 grant 也可能重置熔断。对单用户播放器，这增加会计复杂度且违背用户对“本安装月预算”的直觉。

**已修订：** `ai_budget_months` 按 owner/month 总计，所有入口共用；guard 也属于 owner。principal 只做授权、查询隔离和费用归因，未来子额度只能附加在总限额之下。

费用上界覆盖最终请求的系统提示、契约、基线、描述、输出与推理计量，不能只按用户文字估算或跨语言使用“字符数÷4”。指定模型不能提供可靠上界时，不开放 cloud。

**实施验证：** 多 grant、grant 轮换、官方/MCP 混用、长系统提示、跨月、价格变化和未知费用都不能扩大可花总额。

## 7. AR6：MCP 是入口，不是 AI 服务的基础设施

**源码事实：** [bootstrap.rs](../crates/hertz-studio/src/bootstrap.rs)已供独立服务和 DBX sidecar 共用，可装配内部服务；[lib.rs](../crates/hertz-studio/src/lib.rs)也明确两种形态共用业务逻辑。

**原方案风险：** R4 硬依赖 R2/R3、锁由 CapabilityService 拥有、worker 无条件检查 grant，会使关闭外部接入的官方 UI 也无法生成，并让外部客户端兼容性拖住整个产品闭环。

**已修订：** AiService 从原 bootstrap 直接装配；官方调用使用可信 local-owner 主体，外部调用才使用 grant。身份、锁、契约是共享小模块，MCP adapter 不拥有它们。R3 本地草稿和 R4 内部任务无需等待 MCP 发布，不增加内部 HTTP 回环。

Rust MCP SDK 仍需短期兼容验证，不能因为采用 Rust 就将 SDK、MSRV、stdio 或背压视为已验。registry 也只覆盖有限 AI 操作，不扩展为全站通用 Agent/插件框架。

## 8. AR7：认证、监听和出网要在真实接线处成立

**源码事实：** [routes.rs](../crates/hertz-studio/src/routes.rs)的旧 API 主要由全权 require_token 包围；[main.rs](../crates/hertz-studio/src/main.rs)允许配置不同 bind；[public_net.rs](../crates/hertz-studio/src/public_net.rs)限制公网地址，但现有 client 允许公网重定向。已有 [secrets.rs](../crates/hertz-studio/src/secrets.rs)提供发行版隔离的 SecretBackend。

**原方案风险：** 新 grant 会被旧中间件挡住，或为了接线被错误赋予全权。固定连 127.0.0.1 无法连接仅绑具体网卡/IPv6 的服务；把新路由直接加到 0.0.0.0 又会扩大暴露范围。通用资源客户端的重定向/超时策略也不适合带密钥的付费 POST。

**已修订：** 受限门面使用独立认证路由组；官方管理继续原认证。首期只在独立主 listener 绑定 IPv4 127.0.0.1 时开放实验 MCP 门面，其它绑定明确不支持，不为此新建服务器。模型专用客户端复用地址检查规则，但禁重定向、环境代理和 cookie，流式限制所有响应的实际字节。凭据复用原 SecretBackend，不增加第二套保险库。

**实施验证：** 专用凭据不能访问旧 API/管理接口；非支持 bind 不发布可用发现；失败大响应、重定向、DNS、跨 origin 和无钥匙串环境按声明失败，不静默降低要求。

## 9. AR8：渐进搜索要保留服务端保护

**源码事实：** [online/mod.rs](../crates/hertz-studio/src/online/mod.rs)中的直接 search 进入 provider registry；6 秒总期限在 [aggregate.rs](../crates/hertz-studio/src/online/aggregate.rs)的 collect 中包住每源 future。当前不能据此认定单源接口也拥有同样总期限或共享搜索 semaphore。

**原方案风险：** 前端改为单源渐进请求后，慢源可超出原聚合总期限；多页面、HTTP 和 RPC 各自限并发也不限制整个服务，作废 UI 结果不能取消实际网络工作。

**已修订：** R1 明确新增统一入场与单源总期限，位置在全部入口实际经过的共享搜索路径。旧聚合复用它，不重复占额；排队有界、许可覆盖执行/清理。保持来源分组先可用的 UI 方案，无需新增搜索任务表、SSE 或持久查询系统。

**实施验证：** 多页和两种传输混合并发、旧聚合并存、慢响应、取消、额度满与等待超时。

## 10. AR9：重采样专项无需先重写 DSP 架构

**源码事实：** [cpal_backend.rs](../crates/vmusic-audio/src/cpal_backend.rs)在解码线程中执行 Resampler 和声道映射；输出回调在设备域执行六段 EQ、增益与软限幅，当前设备输出选 float32。

**原方案风险：** 直接把候选链规定为“源域 EQ/卷积 → 重采样 → 末端保护”，会把已有 EQ 搬域，影响 crossfade、滤波历史与延迟；为了高质量重采样提前建设通用处理图、整数 dither 等，远超 S1 用户收益。

**已修订：** S1 只替换解码侧重采样，验证块处理、延迟、flush/reset、声道和时钟；既有设备域处理保持。全链顺序、参数 EQ、卷积、真峰值和整数输出各自在明确需求和测量后再定。Rubato 是候选原型依赖，未完成版本/API/MSRV/包体验证前不冻结为正式选型。

## 11. 继续保留和后置的选择

| 选择 | 结论 | 实施条件 |
| --- | --- | --- |
| Rust + tokio + 现有 axum | 保留 | 新路径留在原应用服务，不引入第二个播放器 |
| SQLite + 现有 store | 保留 | 短事务、单服务端 owner、持久幂等与费用事实；不加 Redis/消息队列 |
| Rust MCP stdio | 保留为首选 | SDK/MSRV/客户端互操作验证；模式在 bootstrap 前分流 |
| 现有浏览器舞台和分享 codec | 保留 | 纯物化/临时层重构有旧行为对照 |
| 单 provider、用户自配模型 | 保留 | fake 底座、真实效果和可靠价格上界均通过 |
| 512 output tokens、30 秒执行、5 美元月额 | 候选参数 | 按指定模型/代表任务验证，不当作普遍适用常数 |
| 外部自动推送工坊、离线完整预置、DBX 外部桥接 | 后置 | 有真实需求后独立定义目标身份、传输与提交回执 |
| 通用 Agent、动态生成代码、向量数据库、完整 DSP 图 | 当前不引入 | 尚无证据证明它们是下一阶段闭环的必要条件 |

26 净工程周只保留为初始容量草案。SDK/启动分流、纯物化/预览和 fake provider 崩溃恢复应先分别做小规模试验，再逐任务重估；不能因图和表变完整就认为排期已被证明。
