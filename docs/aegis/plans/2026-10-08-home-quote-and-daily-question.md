# 首页卡片留白填充：名人名言（先行）与每日一问（后续）

Goal: 首页「正在播放」卡片的文案块与封面之间有一整列空白（实测约 270px），所有主题下都空着。
先用「名人名言」把它填实；「每日一问」作为第二期单独排期，理由见文末。

Architecture: 落点是**业务层**（`index.html` + `home-dashboard.css` + `home-dashboard.js`），
不放任何皮肤 CSS —— 这块空白在十套主题下都存在，写进皮肤会导致「只有清风有内容」。
名言取自一言网，启动拉一次落本地缓存，点击换一条只在本地换。

Tech Stack: 原生 JS / CSS、localStorage、Node、Chromium。

Baseline/Authority Refs: 用户截图（首页卡片红框区域）、`home-dashboard.js`、
`home-dashboard.css` 的 `.home-primary`、一句话（hitokoto）开放接口。

Compatibility Boundary: 不改 `.home-primary` 的网格列定义、不改卡片高度、不动播放链路与
封面解码；关闭开关时整块不渲染，不留空白 div 或多余分隔线。

## 现状诊断

`.home-primary` 原来是 `grid-template-columns: minmax(0,1fr) auto`：

- 文字列吃满剩余宽度，但曲名 / 艺人 / 按钮都很短（最宽也就十几个字）
- 于是第 1 列右侧到封面之间空出约 270px，视觉上就是一块无意义的空白
- 现有 `@container (max-width:560px)` / `(max-width:340px)` 两档断点都只调间距与封面尺寸，
  **没有处理这块留白** —— 空白在所有宽度下都存在

## 结构改版：封面左置（已实施）

用户最终选定的形态（**方案 B**）：

- 网格改成 `auto minmax(0,1fr)`：左列定宽 132px 放**封面 + 主操作**，右列吃满剩余宽度
- 按钮移到封面正下方，宽度与封面一致
- 歌名歌手**不再常驻**（大标题取消），改为**悬停 / 聚焦封面时从封面底部浮出**
- 状态行右侧补一句「曲名 - 歌手」作为兜底 —— 封面浮层只在指针/键盘下出现，
  触屏根本没有 hover，没有这一行就等于首页第一眼丢掉了"现在在放什么"
- 右侧整列留给每日名言，字号 `--fs-xl`（19px），它是这张卡的主角

实测几何：胶囊 `132px 621px`，按钮与封面左边缘偏差 0px、宽度完全一致，
名言块吃满右列 100%（65px 高）。原先那块 270px 空列不复存在。

### 数据源（实测踩过的坑）

- 一言网 `https://v1.hitokoto.cn/`：中文、可按分类取（`c=i` 诗词 / `d` 文学 / `k` 哲学 / `h` 影视），
  返回 `hitokoto` 正文 + `from` 出处 + `author`。免注册免 key。
- ⚠️ **必须串行 + 带间隔，且 URL 要带自增参数**。实测 8 个并发请求会被 CDN
  合并成 3~4 个唯一 id（同一句反复出现）；即使串行 220ms 仍会相邻重复。
  最终做法：`?_=<dayKey>-<seq>` 绕开合并 + 140ms 间隔 + 撞重复时 320ms 重试一次，
  实测拿到 8 条不同句子。
- ⚠️ **抓到 1~2 条不算成功**。曾就此写入缓存，语料池只剩一条 → 「换一条」永远是同一句，
  而且会把原本完好的缓存**覆盖成残缺的**。现在不足 3 条时并入内置兜底凑满，
  且**不写盘**，避免污染下一次启动。
- ⚠️ **点击「换一条」不打网络**，只在本地缓存里转（实测 0 次请求）。
- ⚠️ **CORS 目前可用**（浏览器直连 v1.hitokoto.cn 正常，实测取到 8 条真数据）。
  若将来被禁，走 Rust 后端代理（本项目本来就是 Rust 服务）。

### 纪律

- 不用 `Math.random()`：按当天日期做种子，同一天刷新位置一致
  （与项目里 stanza 那条「渲染层零 Math.random()」一致）
- 皮肤 CSS 禁颜色字面量的规矩同样适用：这里只用 `var(--…)`，十套主题各自正确
- **落点必须在业务层**（`home-dashboard.*` + `index.html` + `app.js`）。
  已核实六套皮肤对 `.home-*` **零覆盖**，所以一处改动六套皮肤同时生效；
  写进任何皮肤 CSS 都会变成"只有那个皮肤有内容"。

## 第二期：每日一问（后续考虑，本期不做）

**结论：市面上没有现成的「程序员基础知识问答」开放接口。**

调研结论（2026-10-08）：

| 方向 | 结论 |
|---|---|
| 面试题库站点（面试鸭等） | 是网页不是 API，没有可用的开放接口 |
| 第三方 LeetCode API | 有（`leetcode-api-pied.vercel.app`，免 key），但那是**算法题**（要写代码），不是基础知识问答 |
| 开源 trivia API（如 OpenTDB） | 是通识/学科题，不是程序员基础知识 |
| AI 实时生成 | 要 LLM 调用、要 key、要等网络 —— 顶栏/首页这种位置不该等 |

因此三个候选方案：

| 方案 | 代价 | 适合度 |
|---|---|---|
| **A. 内置题库**（推荐） | 要整理 100~200 道题 + 答案 | ✅ 最契合：离线、零延迟、无隐私顾虑、可控 |
| B. 蹭第三方题库 API | 无合适接口、稳定性差 | ❌ |
| C. AI 实时生成 | 要 key、要网络 | ❌ |

### 若要做，建议的形态

- **题库走内置 + 按当天日期选种子**，与 `daily.js` 已有的「规则跑本机」同一路子
- 位置可复用本期名言那块，但要**可切换**（设置项二选一 / 都开），因为两者同属「每日一条」
- 交互上「每日一问」比名言多一层：**要能翻出答案**。建议点一下展开，
  且答案色用 `var(--brand)`（「正在生效」的角色色）
- 可能需要难度分级（基础 / 进阶）与分类（网络 / 操作系统 / 语言 / 数据库）
- 同样绝不能每次点击都打网络：题库内置，展开答案是纯本地操作

### 待定问题

- 名言与「每日一问」并排还是轮换？两者同属「每日一条」，并排会挤，轮换则一次只看一条
- 卡片高度是否允许再涨一点？两者都开时需要更多垂直空间
- 题库由谁整理、是否要带出处与讨论链接

### 架构对齐

- 保持 `home-dashboard.js` 只读快照的既有约定（迟到历史/封面不覆盖当前曲）
- 未新增渲染器、依赖或第二套播放时钟
- 名言模块**独立于播放事件**：`update()` 每换一首歌就跑一次，名言混进去会让
  每次换歌都白跑一遍网络与存取，还把它和「封面不能重复解码」的时序逻辑绑在一起
- 换歌时状态行与封面浮层**两处一起更新**，否则浮出会露出上一首的歌名
