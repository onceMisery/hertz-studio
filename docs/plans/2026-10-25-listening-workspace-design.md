# 一起听独立工作区：原型对齐与功能设计

状态：界面方向以用户提供的六张桌面/手机原型为准；互联网服务接入和手机音频形态等待用户补充，相关实现不先行假定。

## 目标与已有基线

“一起听”是 Hertz 主界面的入口。进入后展示专属工作区，包含大厅、房间播放、邀请、共同队列与聊天；桌面使用侧栏和主次分栏，手机使用独立页面、底部导航和大封面播放页。用户要求包含原型功能，不能以纯视觉稿、假数据、不可用按钮或把全部表单塞进一页作为交付。

基线为 `acbe8b4`。现有 `HertzRoom` 管理会话、服务快照、请求与未知操作回执；AppState 唯一拥有业务队列，共享 RenderCore 产生 PCM，原生 Receiver 唯一拥有设备输出。受限房间 TLS 与本机全权回环 API 分离。这些所有权继续生效，见 ADR-0011。

主要读取范围：`plugin/ui/{app.js,room.js,room.css,room-transport.js,index.html}`、房间 `contract.rs/host.rs/guest.rs/manager.rs/resources.rs`、LAN `members.rs/discovery.rs`、原生输出与现有前端/端到端验收。项目已有 QR 编码器和收藏模块，可复用；当前没有互联网好友、公共房间目录或手机接收应用。

| --- | --- | --- | --- |
| 大厅 | 搜索/分类、房间列表、创建与加入、当前房间卡片 | 单列房间卡、搜索/筛选、底部导航 | 真实发现/目录结果；名称搜索；分类取真实声明；显示准确数量；创建/加入/入房申请 |

主应用和工作区之间有明确的返回入口，返回不会退出健康房间。房间外的紧凑播放栏继续复用当前播控；工作区内显示自己的播放区，避免双份控制遮挡。离开页面、离开房间、关闭房主服务分别保持原有生命周期语义。手机端由页面切换承载内容，不将桌面长表单缩成一列。

## 功能合同与真实数据

| 原型功能 | 当前能力 | 实施要求 |
| --- | --- | --- |
| 建房、一次性邀请、指纹核验、成员撤权 | 已有 | 重组交互，保留原生信任与权限复查 |
| 播放/进度/模式/队列/本机音量 | 已有 | 复用现有请求与回执，不另建播放器或乐观宣称同步成功 |
| 共享封面、标题、歌手、专辑、时长 | 已有受限资源 | 使用真实授权资源；无封面有设计过的空态；不展示本地路径 |
| 风格/BPM | 现有共享投影不提供 | 只展示实际可获得的元数据；缺失时隐藏标签，不填示例值 |
| 在线人数、成员同步/缓冲、房间开始与时长 | 部分已有 | 增加有界、带时间戳的房间投影；区分在线成员、音频输出与遥控端；不能将网络 RTT 称为声学误差 |
| 点歌人、点赞、投票排序、歌曲聊天卡片 | 尚未实现 | 由房主统一裁决；稳定 member/queue instance 身份；请求幂等与权限复查；纯文本与结构化资源引用分离 |
| 活动流 | 尚未实现 | 由已提交的房间操作生成；有界保留、序号去重；不把历史事件重新当实时弹幕播放 |
| QR 与复制/分享邀请 | 可复用 QR/剪贴板 | 编码当前有效的邀请能力；可过期、撤销；生成/复制失败有明确反馈；凭据不进入日志与公共快照 |
| 短房间码与直接加入 | 尚未实现 | 短码用于查找/申请，不能替代高熵邀请和授权；房主关闭后失效；请求限流、容量和审批队列有界 |
| 成员邀请他人、新成员审批 | 尚未实现 | 明确独立权限；房主可处理申请/撤销；审批前不能取得 PCM、聊天或资源读取权 |
| 大厅公开卡片、分类与推荐 | 现有 mDNS 仅提供候选房间 | 明确可公开的摘要与可发现设置；推荐只能使用真实数据；缺少结果时展示空态，不使用原型示例房间 |
| 附近设备、在线好友、最近一起听、提醒/邀请 | 仅已有候选房间和最近房间凭据 | 好友/设备在线必须有真实身份与连接数据；点击邀请才发送；不将 mDNS 地址当作信任或任意扬声器的兼容声明 |
| 手机远程操作/手机同步出声 | 当前界面只访问本机鉴权 API | 依据用户补充选择原生接收应用或受限远程入口；不能将全权 API 直接绑定局域网，也不以 responsive CSS 宣称手机接收功能完成 |

队列投票只调整可变的未来后缀，当前播放实例和已冻结音频前缀保持时间线合同。每个成员对同一实例的投票至多一份，重连不重复计票；同一歌曲再次排队是新实例。排序采用票数、原始点歌顺序和实例 ID 的确定性规则。自动排序模式和手动模式由房主显式选择，不能每次前端刷新重新排。

收藏属于用户的收藏数据；房间票数属于当前房间实例；二者不能合用一个计数。共享资源 ID 不能假装成本机曲库 ID，也不能绕过资源权限。歌曲消息仅引用获准资源，加入队列/投票仍走正式房间请求。

## 视觉与交互约束

遵循用户原型，使用紫黑底色、低对比紫色面板、玫红主要动作、青色健康状态，以及圆角卡片和细边界。其优先级高于通用设计技能对紫色和渐变的默认建议。沿用现有原生 JS/CSS 与图标体系，不引入 React、Tailwind 或第二套构建链。

样式限定在工作区，使用自己的语义颜色/间距/层级变量；主应用皮肤不改色。桌面侧栏约 264–304px，主次栏采用 `minmax(0, 2fr) minmax(280px, 1fr)`；中等宽度收起次栏到页面切换；手机单列，考虑安全区、动态视口、键盘和固定输入区。按钮触达至少 44px；可见焦点、禁用原因、加载/空态/失败态、返回与焦点恢复都纳入交付。支持 reduced-motion，动画只改变 transform/opacity。

示例昵称、房间码、128 个房间、2417 个赞、0.18 秒、68% 缓冲等只用于理解原型，不能作为产品默认数据。未取得有效遥测时显示等待/不可用，不能显示“已同步”。用户可在同步详情查看原生时钟、缓冲、欠载和重连原因；主播放页保留简洁、准确的状态摘要。

## 实现路线选择

1. **推荐：现有房间控制器 + 专属工作区视图 + 正式领域扩展。** 保留操作、资源、权限和音频基础，将页面组件与控制器拆开；投票、审批等通过共享 Rust 合同落地。变更范围与原型一致，继续只有一份业务和音频所有权。
2. 全量替换为前端框架：能够组织页面，但增加构建、皮肤和插件适配成本，不解决缺失服务能力，当前不采用。
3. 单独搭建一套同频应用：可独立发布，但会复制身份、曲库、队列和播放事实，不符合现有完整交付与可扩展要求，当前不采用。

推荐路线中的前端视图仅负责 DOM、页面状态和用户意图。网络、会话隔离、回执与资源释放由现有房间控制器持有。后台的房间协作状态由 Host 持有，业务队列仍由 AppState 持有；新社交或远程连接能力通过明确边界接入，不在页面上猜测服务状态。

## 正在补充的两项信息

1. 互联网好友/异地一起听：已有服务的接入信息，或由本项目提供可自建的身份、目录和连接服务；若用户选择本轮仅局域网，则相关互联网功能明确转入后续范围。
2. 手机：直接出声的原生接收端、遥控/点歌/聊天客户端，或接受不同同步精度的浏览器音频端。三者对应的音频、信任和部署合同不同。

这些选择不改变用户已确定的视觉方向与页面结构；决定新增后端和移动接收实现范围。不能用隐藏或不可点击的原型按钮代替这些选择的真实实现。

## 验收与交付

- 桌面 1440/1280/1024px，手机 390/360px 与横屏：无横向溢出，导航、键盘、底部安全区和长内容可用；对照原型保存真实截图。
- 两独立成员完成创建/发现/加入/邀请/权限、播放/seek、点歌/投票/重排、歌曲卡片聊天、审批、返回主应用与离开/结束；核对每个操作的服务器结果。
- 重连/换房/撤权/重复提交/过期邀请/审批超额/资源失效/聊天限流有明确行为，页面不重复发送相对写命令、不显示假终态。
- 领域测试覆盖重复实例投票、平票排序、冻结后缀、成员退出/重连身份、审批前隔离和权限持续复查；扩展协议时同步版本与不兼容拒绝。
- 原生音质和生命周期回归继续有效；新版本二进制需重新绑定验收身份。仅 UI 变更不虚构新增硬件支持面。
- 手机原生出声与互联网路径的专属验收随用户选择补入实施计划；没有对应设备或部署实测，不宣称完成其发布验收。

架构影响：新增协作/入房合同需要更新 ADR 与 API 文档；本文是待范围补充的设计，不把尚未实施的选择记为已生效架构。
