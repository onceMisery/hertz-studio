# 资源占用优化（2026-10-21）

本轮保持音频转换参数、画面分辨率、场景内容及播放时帧率预算，优化重复工作、临时分配和发布资源。保留原工作区的 AI/创作舞台修改；未替换用户正在运行的服务。

## 实现

- 音频 actor 只发布变化的快照，命令回执前仍同步共享状态；结束、衔接、seek 和错误事件保留。
- 实时频谱预分配 Hann、FFT 输入和 scratch，复制 tap 后释放采样锁；播放解码复用转换缓冲。中性 EQ 走等价直接路径，保留其它 DSP。
- 节拍解码边读边重采样，仅保留一个源样本及分析率输出，复用转换和 FFT 缓冲。480 秒分析率选择、720 秒截断、全局插值相位和尾段语义保持；未知时长在 480 秒前保留两种分析率候选。
- 暂停时让歌词滚动、能量和节拍释放收敛，再停止帧门；控制、seek、主题、音量和新打开的视图仍会唤醒。重复快照不重复写控件、首页或媒体会话。
- 创作舞台复用内部参数和每视图矩阵，按实际 CSS 色值变化重解析颜色；公开 runtime 快照仍独立。歌单封面只缓存最终结果，并丢弃失效请求；曲库查询完成后保留至多 1024 条无活跃引用的备用元数据，当前列表、详情、队列、选择和播放引用均受保护。
- 三个 3D API 共享一个同步 classic-script 运行库；发布暂存阶段压缩 JS/CSS，保留开发源码。独立服务只嵌入 gzip 资源，浏览器直接接收预压缩字节，无压缩客户端按资源首次访问解压缓存。首页单独注入令牌；发布 HTML 仅保留公开入口。

| 同一次页面采样的 DOM MutationRecord | 2500 | 224 |

| 16.8 秒 STFT 的 8192 字节分配 | 723 次 | 2 次 |
| 192kHz/2 秒重采样测试的保留缓冲 | 源 PCM 单独 1536000 字节 | 输出容量及状态共 262208 字节 |
| 100 个各含 2000 首合成曲目的歌单封面解析后保留曲目数组 | 100 份 | 0 份 |

页面对照使用同一个已有后端、无头 Chrome、1440×900 和相同隔离曲目，分别提供优化前保存的 UI 与优化后的 UI。另用新构建的 Standard 后端及压缩后的完整 UI 验证：播放后稳定暂停 6 秒，rAF、重复状态快照、DOM 变更均为 0，页面错误为 0；播放期间歌词/能量预算仍为 60/20fps。新二进制的真实 HTTP 页面成功加载 121 个 gzip 资源，三个场景 API 就绪，令牌注入及 identity 回退正常。

最终压缩产物保留文件开头的许可证/版权声明。直接执行 Rust `build.rs` 的 Release 分支验证，Standard 的 128 份内嵌 JS/CSS 从 4250573 字节 identity 内容变为 1284459 字节 gzip，Full 的 130 份从 4310280 变为 1302540 字节；均已逐文件解压往返校验。这是内嵌资源字节量，不是链接后的 exe 大小。

分配次数与保留容量是确定性测试数据；合成歌单是压力样本。DOM 记录不代表实际绘制次数，rAF 数量不代表整机 CPU，JS 堆不包括浏览器进程和显存。没有据此承诺总体 CPU/RAM 降幅。UI ZIP 为实际资源压包，比较时其它当前源码保持一致，仅恢复旧场景包及旧 edition generator；不含 sidecar，不能当成最终 exe 或完整 dbxp 的缩减比例。未生成同版 Release exe 的前后对照。

## 后续待优化：Rust 源码文件体量（2026-10-22 登记，本轮不实施）

本轮删除浮光与潮汐皮肤后，顺手核了服务端 Rust 文件的体量。结论不是“行数多就必须重构”，而是区分**生产代码体量**和**测试体量**：

| 文件 | 总行数 | `#[cfg(test)]` 前生产行数 | 主要问题 |
| --- | ---: | ---: | --- |
| [`state.rs`](../crates/hertz-studio/src/state.rs) | 6,765 | 约 4,423 | 单个 `impl AppState` 从 924 行铺到测试模块前，约 3,500 行；播放、队列、扫描、在线元数据、观众计数和发现文件共用一个类型，定位一条锁序要跨全文件读 |
| [`ai/jobs.rs`](../crates/hertz-studio/src/ai/jobs.rs) | 7,384 | 约 2,405 | 总行数最大，但 2,406 行以后几乎全是测试；先拆测试即可，业务逻辑暂不是首要瓶颈 |
| [`routes.rs`](../crates/hertz-studio/src/routes.rs) | 4,900 | 约 3,410 | 223 个函数但文件自述“薄 handler”；主要风险是 HTTP 与 RPC 契约漂移，不按行数优先拆 |
| [`cpal_backend.rs`](../crates/vmusic-audio/src/cpal_backend.rs) | 4,137 | 约 2,126 | 设备回调、重采样与 DSP 耦合，拆分会影响时钟与延迟语义，优先级低于 `state.rs` |

下一轮建议从 `state.rs` 开始，且只做**可逆的模块边界拆分**，不改并发语义：

1. 先按职责抽出子模块：播放与队列、在线元数据与下载、扫描进度、观众/发现文件、DSP 与监听统计。`AppState` 继续作为字段与锁的 owner，子模块只通过明确的 `impl AppState` 分块或 helper 访问，避免把 `play_commit`、代际和 viewer 计数拆成多把隐式锁。
2. 每次只搬一个职责，并保留现有行为测试为门槛：`cargo test --locked -p hertz-studio --lib state::tests` 与 `ai::facade::tests` 必须同轮通过；涉及播控时再跑 `check-player-races.js` 或对应浏览器检查。
3. `ai/jobs.rs` 的测试拆成 `ai/jobs/tests.rs` 或按“受理、派发、取消、恢复、结算”分多个测试模块；拆完用 `cargo test --locked -p hertz-studio --lib ai::jobs::tests -- --test-threads=1` 证明用例数量与结果不变。
4. `routes.rs` 暂不拆。若后续要按端点域分文件，必须保留 `router()` 单一入口和现有 `pub(crate)` 请求体复用，防止 HTTP、RPC、MCP 三套入口各自漂移。

验收口径不是“每个文件都低于某个行数”，而是：一次播控或授权变更能在一个职责模块内读完主路径，锁序和完成事实仍能由现有测试证明；拆分不新增运行时分配、不改变事件顺序、不扩大公开 API。
