# ADR-0002 · 内存里的表都要有界，且淘汰策略分两种

状态：生效（首次记录 2026-10-07）

## 决定

所有只活在内存里、随「用过的曲目数」增长的表都必须有上限，且**上限的语义写在这里**。
淘汰策略只有两种，按「忘掉一批的代价」选：

- **逐条淘汰最旧的写入**（`BoundedMap`）：代价是单条信息要重取一次。用在读取位于关键
  路径、且丢一条只影响一首歌的地方 —— 在线元数据、节拍任务态、音质上限。
- **满了整表清**（`RelayMemory`）：代价是「可能多试一次坏流」。只在一次故障恢复期间
  活着、链一结束本来就该作废的地方。

判据是一句话：**清空会不会一次性丢掉当前队列全部曲目的关键信息**。会，就用逐条淘汰。

## 边界与 owner

| 数值 | 现在是多少 | 定义在哪 | 改它要一起改什么 |
| --- | --- | --- | --- |
| 在线元数据快照条数 | 8192 | `crates/hertz-studio/src/state.rs::ONLINE_META_CAP` | 播放历史里标题退化成平台 id 的可见面（被淘汰后重入队会补回） |
| 节拍任务态条数 | 8192 | `crates/hertz-studio/src/state.rs::STAGE_BEATS_CAP` | 只影响幂等：最坏是重开一次分析，不影响正确性 |
| 接力坏流记忆条数 | 64 | `crates/hertz-studio/src/state.rs::RELAY_TRIED_CAP` | 候选池缩小速度；整盘换队/成功提交时本来就会清 |
| 未落盘节拍图的保留条数 | 8 | `crates/hertz-studio/src/state.rs::BEAT_VOLATILE_CAP` | 数据目录只读的设备上的内存上限（一张图几十 KB 到几 MB） |
| 节拍键→曲名的保留条数 | 256 | `crates/hertz-studio/src/state.rs::BEAT_LABEL_CAP` | 状态面板那行还认得出「在算哪一首」；被淘汰只让那一格退回键前缀，不影响分析 |
| 首跳票据条数 | 512 | `crates/hertz-studio/src/ticket.rs::TICKET_CAP` | 一次性票据的存活与兑换窗口 |
| 前端在线元数据暂存条数 | 400 | `plugin/ui/online.js::META_STORE_MAX` | localStorage 配额；超了砍最旧一批 |

## 禁止回退

- 不许给这些表加「无上限」选项。上限是安全网，取值远高于正常使用规模（一张五千首的
  歌单也只占 `ONLINE_META_CAP` 的一半多）。
- 不许把逐条淘汰改成整表清空：那会一次性丢掉当前队列全部曲目的标题，播放历史与
  接力匹配会同时退化。
- 不许让前端暂存成为服务端的替代品：`remember_online_meta` 保留已知出处与响度标签，
  新快照没带这些字段不等于「没有」。
- 读取路径不许为了 LRU 而拿写锁（这是「写入即最新」的理由）；要改 LRU 就整体改，
  别在某个读点上偷偷 touch。
