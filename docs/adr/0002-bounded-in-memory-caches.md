# ADR-0002 · 内存里的表都要有界，且淘汰策略分两种

状态：生效（首次记录 2026-10-07）

## 决定

所有只活在内存里、随「用过的曲目数」增长的表都必须有上限，且**上限的语义写在这里**。
淘汰策略只有两种，按「忘掉一批的代价」选：

- **逐条淘汰最旧的写入**（`BoundedMap`）：代价是单条信息要重取一次。用在读取位于关键
  路径、且丢一条只影响一首歌的地方 —— 在线元数据、节拍任务态、音质上限。
- **满了整表清**（`RelayMemory`）：代价是「可能多试一次坏流」。只在一次故障恢复期间
  活着、链一结束本来就该作废的地方。

判据是一句话：**清空会不会一次性丢掉当前队列全部曲目的关键信息**。会，就用逐条淘汰。

## 禁止回退

2026-11-20：封面条数与声明字节分别有界。app 原封面缓存持有 DBX 返回的有界 UTF16 源；队列、Stage、Backgrounds、普通曲库行、歌单、MediaSession 和预加载用途显式借用。缓存失效或淘汰只退休缓存用途，最后实际用途清除 URL 后才归还源额度。图片准备使用原 owner 的有界等待队列；额度忙不能把正常整页封面永久标为无图，卸载和旧图片事件不能提交或取消新请求。普通外部 HTTP 的 DOM/CSS 展示保持浏览器加载语义，不将不可观测的浏览器解码/合成缓存冒充声明字节。

同日录制沿原 `VideoExport` owner 在开始时预留视频块与最终 Blob 共存空间，单轮容量按当时额度冻结为 8–32 MiB；保留 256 MiB 硬保护和 10 分钟时限。32 MiB 视频块与等量 Blob 的工作上限为其它舞台资源保留容量，不抬高 128 MiB 页面策略，也不表示设备性能保证。结果缓存、下载与工程消费者按实际租约持有 Blob，最终用途结束才归还。源码常量、UI 容量、拒绝恢复和验证入口共同维护于[视频导出](../video-export.md)。

- 不许给这些表加「无上限」选项。上限是安全网，取值远高于正常使用规模（一张五千首的
  歌单也只占 `ONLINE_META_CAP` 的一半多）。
- 不许把逐条淘汰改成整表清空：那会一次性丢掉当前队列全部曲目的标题，播放历史与
  接力匹配会同时退化。
- 不许让前端暂存成为服务端的替代品：`remember_online_meta` 保留已知出处与响度标签，
  新快照没带这些字段不等于「没有」。
- 读取路径不许为了 LRU 而拿写锁（这是「写入即最新」的理由）；要改 LRU 就整体改，
  别在某个读点上偷偷 touch。
