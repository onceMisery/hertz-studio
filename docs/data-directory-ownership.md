# 资料目录的服务所有权

日期：2026-11-07（11-06 开始实施）。范围：[桌面交付 A08](desktop-release.md) 的同资料目录互斥与原生重复打开。当前工作树实施，尚未发布。

## 启动边界

独立 HTTP 服务与 DBX sidecar 都先调用 `bootstrap::prepare`：创建并 canonicalize DataDir → 获取 `service-owner.lock` 内核锁 → 获取原有 AI runner 内核锁 → 读取配置。只有成功获得这些资源才返回不可复制的 `Prepared`，`bootstrap::boot` 消费它后才打开数据库、迁移、恢复状态及初始化音频。

本地端口、edition 和 HTTP/stdio 形态都不参与锁身份；路径别名指向同一个物理目录时不能形成第二个服务。不同 DataDir 仍可并行。失败返回稳定的 `data_dir_busy` 原因，原服务的配置、token、数据库、发现记录与音频不被新进程接管。

服务锁由 `AppState` 持有，后台任务和退出工作仍引用状态时不会提前释放。锁文件持续存在，退出或崩溃由操作系统释放句柄；不根据 PID 文件猜占用，不删除锁文件“解锁”。Windows 使用现有 fslock 的 `LockFileEx`，Unix 使用 `flock`；锁句柄不继承到新启动的进程。

AI 许可仍由原 AI 锁/业务守卫负责。把 AI 锁获取提前，是为了识别已经运行的旧版本：本轮之前的播放器/DBX 已持有它，可以阻止新版加入旧 owner 正在使用的资料。旧版在新版之后手工启动时不会遵守新增服务锁；更老、从未持有这些锁的程序也不在协作协议内。安装器仍需验证旧进程退出和安装文件占用，不能声称新增锁可以控制所有历史程序。

`--describe`、帮助/版本、MCP 适配进程和离线评测仍在业务初始化之前分流，不争抢播放服务所有权。DBX 不建立原生主窗口、HTTP listener、后台播放或 SMTC owner。

## 原生重复打开

旧的“服务端口 + 1”无身份 focus socket 已退役。它既无法表达同一目录的随机端口，也可能将另一个 profile 的端口响应当成自己的窗口；主窗口也不再为了查端口提前加载/写默认配置。

新 `--window` 启动失败于 DataDir 锁时，只读该目录的 `vmusicd.json`（上限 16 KiB）和 token（上限 256 字节），核验 edition、规范化目录、token 一致性和合法服务实例 UUID，再通过既有回环 HTTP 发 `POST /v1/window/focus`，body 为 `{serverInstanceId}`。没有第二份长期凭据或管理服务器。

接口使用原 Bearer/cookie 鉴权，并核对当前服务实例、真实原生 owner 和事件接收方是否存在。普通浏览器服务返回 404；无凭据返回 401；旧实例或窗口尚未就绪/正在退出返回 409。客户端关闭代理/重定向，单次请求 750 ms、总恢复等待五秒、响应上限 4 KiB。只有确认回复属于原实例才把第二次启动记为成功；失效发现记录不会放行第二个服务，也不会触发新服务重新尝试写库。

源码和预览启动脚本、原生生命周期检查已改用这一接口；没有继续保留无身份旧端口作为回退。托盘与 HTTP 最终都向现有窗口事件循环发送恢复动作，不新建主窗口。

## 旧目录迁移

显式 `--data-dir` 或 DBX profile 不再迁移不相关的默认旧目录。默认根目录从 `mmusic-studio` 改名时，先拿父目录的迁移锁，再检查旧主目录和已有 `dbx-plugin` 子目录的服务/AI 锁。Windows 不允许持有目录内打开句柄时改名，因此检查锁在同卷 rename 前释放；迁移锁覆盖整个检查与改名窗口，新的 prepare（含历史目录的别名）也遵守该锁，在创建新目录前参与准入。旧服务仍占用时保持原路径；rename 失败则停止启动并保留原资料，不继续制造空库。已有新旧两个目录时保持原有不自动合并规则。历史旧程序不遵守新的迁移锁，不能在迁移过程中同时手工启动旧版。

这是旧名称迁移的占用保护；数据库 schema 升级备份、安装目录互斥、安装器更新/回滚和跨版本发布资格仍属于后续交付工作。

## 验证

`data_owner` 的真实文件锁测试覆盖在配置读取之前拒绝竞争、失败后释放，以及旧 AI owner；`legacy_migration` 验证根目录与 DBX 子目录占用时不改名、数据保留和释放后成功；focus 的真实 HTTP 测试覆盖鉴权、实例身份与 host 生存期，发现文件解析另验错误目录/edition/token/大小。

[真实进程检查](../scripts/check-data-owner.js)使用独立 Full HTTP 与 DBX SDK stdio 二进制、私有资料、null 音频，覆盖不同端口、目录别名、并行独立 profile、两种宿主互斥、强制结束与 EOF、失败配置、同时启动、旧版本与当前原生恢复。可通过 `HERTZ_STANDARD_BIN` 追加真实跨 edition，通过 `HERTZ_LEGACY_BIN` 追加旧版兼容检查。前轮[最终十组报告](../output/data-owner-1793983486814/report.json)覆盖实际 Standard/Full、旧版与 DBX，记录的源码 SHA-256 已于 11-07 逐项对照当前文件；当前[Full/native release 九组回归](../output/data-owner-1794012615729/report.json)再次验证服务互斥与原生恢复，未重建 Standard。

现有 AI 凭据 owner 检查已更新为“第二进程在启动前被拒绝”，继续检查主服务凭据管理、任务/预算不变与敏感值不落盘。前轮 Full/Standard sidecar 协议冒烟分别 **295/295**、**311/311**，原生窗口/定时/退出 **9 组**；当前 release 的安装与真实包资格另见[程序目录保护记录](windows-install-updates.md)。历史“双服务启动、第二服务仅 AI 禁用”属于旧能力边界；AI 内部守卫仍保留。
