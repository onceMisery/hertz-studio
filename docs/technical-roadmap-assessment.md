## 1. 总体结论

**方案合理，可以按此实施；未发现结构性设计错误。** 它的价值不在覆盖面，而在三件事：对现有代码缺口的描述经核验基本全部属实，因此开出的药方对症；把"完成"的语义（applied/unknown/failed、费用保守结算、资源回收）当成一等设计对象，而不是事后补丁；每个阶段自带否决条件而非愿望清单。主要风险不在设计，而在两点工程现实——**单人容量与方案密度的差距**（4.1）和**有效规范分散在多份文档与一个 git 忽略目录**（4.2）。两者都有低成本缓解手段，不构成推翻重做的理由。

| 维度 | 评价 |
| --- | --- |
| 方向选择 | 正确。Rust 单运行时、前端唯一物化 owner、不引入通用 Agent/第二播放器/JS 引擎，与仓库既有演进（移除内嵌 JS、双版裁剪、单一 Stage 时钟）一致 |
| 事实准确性 | 高。抽查 26 项源码陈述，23 项完全属实，3 项结论成立但表述需修正（见 2.2） |
| 失败语义与资金安全 | 充分。派发标记、unknown 保守计费、终态 CAS、槽位覆盖回收，是同类"AI + 付费"方案最常缺失的部分 |
| 范围纪律 | 强。"不做清单"（§1、§5.2 末、§13）与发布条件绑定，而非无限期挂起 |
| 可实施性 | 设计层面可实施；容量是最大风险（4.1） |
| 文档治理 | 待改进（4.2） |

## 3. 突出优点

1. **药方对症。** 每处修订都能对应到可核验的代码缺口：`require_token` 全量包裹 → 独立路由组 + 专用 grant；`vmusicd.json` 全权 token → 不含 token 的 `ai-discovery.json` + 专用凭据文件；`saveLocalSoon` 400ms → 不落盘的临时预览层；RPC"逻辑照抄" → 六种播控下沉共享入口并返回类型化结果。安全约束都能落到真实代码事实上，不是纸面威胁模型。
2. **把"完成"当设计对象。** outcome 表（ok/draft/accepted/applied/unknown/failed）、"已发出但无法核实不能自动重放"、`dispatchState` 保守计费、"取消任务不代表资源结束"，覆盖了这类系统最常见的三类事故：假完成、重复扣费、资源泄漏。
3. **边界纪律可执行。** §1.1 优先级表把"破坏它的典型失败"写出来；§13 把每个未决事项绑定到"在哪一阶段固定、未解决时阻止什么发布"。
4. **诚实标注贯穿全文。** "计划接口/初始候选值/未实现/本轮仅编辑文档，没有声称运行通过"处处可见，使文档可以当作设计基线而非完成报告。
5. **验证体系分层。** 四类证据 + §12.1 反例矩阵（授权越界、实例错连、满表、墙钟回跳、慢清理等最易被跳过的负向路径）+ "fixture 结论不扩大到真实环境"。
6. **与既有 ADR/复核形成闭环。** 复核记录的 AR1–AR9 全部回写到正文对应章节，无悬空修订。

## 4. 主要风险与建议

### 4.1 容量是最大风险（优先级最高）

方案给 R2 排 3 净周，但 §11 把 R2 拆成 C/G/M/P 四个任务包，每个都要求 §12.1 对应的反例矩阵（授权、实例、短写、播控事实、MCP 互操作、本地门面、发行版矩阵）。按包内证据要求推算，R2 实际更可能落在 5–7 净周；R4（任务 + 账本 + 事件 + 官方 UI）排 4 周，同理可能需要 5–6 周。方案自己承认"26 周仍是初始容量草案"，并给出三个先行 spike（SDK、启动分流、物化/预览各 1–2 日）——方向正确，建议再补一条：

**现在就预约定裁剪顺序。** §5 的每一条都写成"必须"，一旦超支，实施者只能在"整体延期"与"悄悄降级"之间二选一。建议把候选裁剪按顺序写进文档，超出排期时依序启用且每项降级留痕：

1. R2-M 的"真实客户端矩阵"收敛为 1–2 个首发客户端，其余进兼容清单；
2. `ai-discovery.json` 发现协议后置，适配器首发改用显式配置的 host:port（安全性不受影响，grant 认证仍然必须）；
3. 错误码/字段投影全集分批，首发只覆盖 §12.1 反例涉及的子集。

### 4.2 规范来源需要收敛

有效规范目前 = 本方案（含两轮修订覆盖）+ 复核记录 + 产品路线图 + git 忽略目录中的 AI v3（新克隆不存在）。"冲突时以本文修订后的明确约束为准"在评审期可行，实施期会持续产生查证成本。建议：

1. R2 开工前，按方案自己的承诺（§8.3"实施时单一常量定义并进入 ADR"）把数值表与幂等/费用关键语义落成 ADR；
2. 把 v3 中仍被正文引用的语义（幂等键格式、任务状态机、费用结算表）摘录进仓库内文档，消除对忽略目录的依赖；
3. 收敛后给复核记录的 AR 条目加"已回写"标记存档，避免多份文档长期并行演进。

### 4.3 R4 账本的可选简化

迟到 usage 的跨月差额回写（§8.4 结算表第 4 行）是整个费用设计里最边缘的复杂度。首期可考虑：差额计入当前月并带归因标注，待 R5 真实 provider 证明"迟到 usage 真实存在且金额显著"后再决定是否回写原月。guard、不双计、不释放为可花余额等核心保证不受影响。这是可选简化而非缺陷；若实现顺利，保留原设计亦可。

### 4.4 短写幂等满表的公平性

去重窗口是 DataDir 全局 512 条（§5.6/§8.3）。fail-closed（满表在执行前拒绝）方向正确，但单个失控客户端理论上可在 10 分钟内写满窗口，把其它 grant 和播控一起拒掉。建议按主体设子容量（例如每 grant 每窗口 ≤128 条），把拒绝面缩小到肇事者。低概率，属于门面自洽性补强。

### 4.5 基线漂移

核验时 HEAD（`a3f93d6`）已比方案最后核对提交新一个提交，且该提交（浮动胶囊启动/渲染性能优化）恰好落在 R1 的胶囊回归范围内。方案已要求"实施前应再次核对"；建议把 R1 胶囊回归清单与该提交的改动点对照一次。

## 5. 次要建议

1. R2-G 实施内核锁时，顺带核对回环 listener 的 Host/Origin 校验：浏览器进程可直达 `127.0.0.1`，新受限路由组应显式校验 Host 头以防 DNS rebinding 类暴露。现有 listener 是否已有此校验未核验。
2. §8.5 评测集在"长文本"之外，显式加入"接近 16384 字符的合法 intent"样本，与 512 output tokens 上限对撞验证截断率——这是两处数值最可能互相冲突的地方。
3. `rpc/playback.rs` 头部"逻辑照抄"注释在 R2-C 收敛六种播控后同步更新，避免注释与代码语义漂移。
4. §7.4 的接口表补上 §8.4 引用的 `POST /v1/ai/budget-guard/reset`（该表自称"建议入口"而非穷举，补全可防实施遗漏）。
5. `require_token` 内已有 `?key=` overlay 窄授权先例（限 `/v1/overlay/lyric` 与封面，`routes.rs:376-378`），grants 的字段投影设计可直接参照其"服务端窄化"思路；新门面"不接受 query/cookie 传递"与现有 GET `?token=` 形成正确对照，说明该约束有的放矢。
